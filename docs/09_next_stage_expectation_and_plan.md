# 下一阶段开发预期与周期规划

> 规划基准日期：2026-03-30  
> 规划对象：当前世界地图重构后的下一阶段开发  
> 文档目标：明确接下来做什么、为什么这样做、按什么节奏推进

---

## 1. 下一阶段总目标

下一阶段不建议继续盲目铺内容，而应围绕“把当前主框架做稳、做深、做成一个可持续开发的平台”展开。

核心目标可以概括为三句话：

1. 把世界地图主流程做稳
2. 把地点与子场景交互做深
3. 把世界生成从样例版推进到正式版

---

## 2. 下一阶段的开发预期

### 2.1 预期一：世界地图成为真正的游戏主舞台

目前大地图已经可移动、可进入地点，但还需要进一步提升为真正的主舞台。

下一阶段预期达到：

- 玩家进入游戏后，大地图是默认长期停留空间
- 地图中有明确的区域、道路、地点与入口逻辑
- 时间流逝、玩家移动、地点进入能够形成稳定循环
- 大地图 UI 能承担状态展示、提示、基础操作入口

### 2.2 预期二：地点系统成为内容扩展核心

后续新增内容不应再直接堆在 `Region` 上，而应围绕 `Location` 扩展。

下一阶段预期做到：

- 每个区域可挂多个地点
- 地点具备明确类型，例如村庄、城镇、门派、遗迹、秘境入口
- 地点决定可进入子场景与交互类型
- 地点成为 NPC 分布、任务投放、商店功能的主要落点

### 2.3 预期三：子场景从“占位可进”提升到“基础可玩”

城镇、门派、客栈等子场景，下一阶段应至少具备基础可玩性，而不只是按钮跳转。

目标包括：

- 城镇内提供基本功能入口
- 门派内提供至少一个可持续交互模块
- 客栈、商会等场景开始承担实际系统功能
- 子场景 UI 风格和布局统一到 1080p 目标体系

### 2.4 预期四：世界生成进入第二阶段

当前世界生成器已经适配了新结构，但还不够正式。

下一阶段预期：

- 正式整理区域生成规则
- 正式整理地点生成规则
- 把路径、道路、地点关系做得更稳定
- 为后续 NPC 旅行、事件投放、资源分布打基础

### 2.5 预期五：项目管理从“随做随改”进入“按阶段推进”

随着主框架成型，开发管理方式也需要同步升级。

建议将后续开发按阶段拆成：

- 稳定主流程
- 深化子场景
- 升级生成器
- 整理验证体系
- 扩展系统内容

---

## 3. 下一阶段建议开发顺序

结合当前项目状态，建议按以下顺序推进。

### 第一优先级：稳定当前主流程

优先处理内容：

- 世界地图 UI 与交互稳定性
- 1080p / 自适应布局统一
- 世界地图进入 / 返回子场景的状态保持
- 时间系统在主流程中的持续同步
- 关键场景解析与切换稳定性

原因：

如果主流程不稳，后续所有内容扩展都会反复返工。

### 第二优先级：补强地点与子场景

建议优先做：

- 城镇场景功能化
- 门派场景功能化
- 地点类型规范化
- 地点与子场景绑定规则固定下来

原因：

地点系统是新世界架构中最核心的内容扩展载体，越早稳定越好。

### 第三优先级：正式推进世界生成器

建议目标：

- 区域分布规则重写或强化
- 地点生成规则系统化
- 道路与区域连接规则系统化
- 地图表现层与逻辑层继续解耦

原因：

世界生成器是“可重玩性”和“世界感”的来源，但它依赖前两项结构已经稳定。

### 第四优先级：回收旧验证体系

建议做法：

- 保留仍有价值的验证场景
- 移除或标记已过时的验证场景
- 把核心验证重新对齐到当前主流程

原因：

当前项目已不是纯验证型原型，测试与验证方式也要跟着升级。

## 4. 建议周期规划

以下周期按“小团队 / 个人连续迭代”强度估算，适合作为近 6 周开发计划。

### 第 1 周：主流程稳定周

目标：

- 清理世界主场景的剩余结构问题
- 完成主要界面的 1080p / 自适应统一
- 修复世界地图与子场景切换中的 UI 与状态问题

交付物：

- 稳定可运行的主菜单
- 稳定可运行的世界主场景
- 稳定可进入并返回的基础子场景

### 第 2 周：地点系统整理周

目标：

- 明确 `Location` 类型定义
- 补齐地点生成字段和进入规则
- 整理地点与子场景映射关系

交付物：

- 地点类型规范文档
- 地点数据字段清单
- 至少一轮更清晰的地点分布逻辑

### 第 3 周：城镇与门派交互周

目标：

- 给城镇和门派填入基础功能
- 让场景不只是跳转，而是提供实际操作反馈

交付物：

- 城镇基础交互版
- 门派基础交互版
- 至少一个可持续发展的场景功能模块

### 第 4 周：世界生成升级周

目标：

- 重整区域生成与地点生成
- 强化道路与区域连接逻辑
- 优化地图视觉分布的合理性

交付物：

- 第二版世界生成器
- 更清晰的区域、地点、道路关系

### 第 5 周：验证与管理整理周

目标：

- 整理验证场景
- 梳理当前模块状态
- 给后续功能扩展建立更清晰的任务板

交付物：

- 更新后的验证方案
- 模块状态清单
- 下一阶段任务分解

### 第 6 周：垂直切片准备周

目标：

- 从“框架跑通”推进到“可展示的玩法切片”
- 让玩家能经历一次完整的世界探索小循环

交付物：

- 一版可展示的世界探索切片
- 一条从大地图到地点再回大地图的稳定体验链

## 5. 建议的任务管理方式

为了避免后续重构继续失控，建议将开发管理分成两个层次。

### 5.1 文档层管理

建议长期维护以下四类文档：

- 设计文档：描述目标玩法与结构
- 技术文档：描述当前技术实现
- 阶段总结：描述这一阶段完成了什么
- 阶段预期：描述下一阶段做什么

本次新增的两份文档，就是在补齐后两类文档。

### 5.2 开发任务层管理

建议使用三段式任务状态：

- `待做`：已经明确要做，但还没开工
- `进行中`：本周正在处理
- `已完成`：完成并可验证

任务拆分上建议以“可交付块”为单位，而不是以“想到什么修什么”为单位。

例如：

- 世界地图 UI 统一
- 地点进入与返回状态稳定
- 城镇子场景功能化
- 门派场景功能化
- 世界生成器第二版

## 7. 风险与管理提醒

### 风险一：过早扩内容

如果在主流程未稳定前就大量添加地点、NPC、任务，会造成返工。

建议：

- 先稳结构
- 再加功能
- 最后扩内容

### 风险二：UI 与逻辑同步失衡

如果只改逻辑不整理场景布局，项目会越来越难验证；反过来只做 UI 也会变成空壳。

建议：

- 每次功能迭代都带上最小可验证 UI

### 风险三：验证场景继续失真

如果验证体系不更新，后续会出现“单独测试能跑，但真实主流程不能跑”的情况。

建议：

- 把验证标准逐步向真实主流程靠拢

---

## 8. 结论

当前阶段之后，项目最需要的不是再做一批新模块，而是把已经出现雏形的世界主框架打磨成一个真正可持续开发的平台。

因此，下一阶段的管理关键词应该是：

- 稳定
- 统一
- 深化
- 再扩展

如果这一阶段推进顺利，项目就会从“重构中的原型”进入“可以持续迭代的世界探索 RPG 骨架”。
